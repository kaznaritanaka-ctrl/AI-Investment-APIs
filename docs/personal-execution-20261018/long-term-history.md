# 10年後に価値を持つ時系列履歴のための契約要件

2026-10-18の所有者の指示を反映。目標は、今から継続して観測し、10年後にも当時の状態と比較条件を検証できるデータベースを育てること。初回検証のために提示した「正規化履歴30日・保存上限T+31日」は撤回する。10年は価値を評価する時間軸であり、10年経過時の自動削除期限にも置き換えない。

この文書は未承認の実行契約案の修正基準。実収集、実行承認、提供者許諾の取得、権利grant変更、本番deployは行わない。提供者許諾が未確認である事実を、研究目的や保存目標で書き換えない。

## 残すものと、短期に処理するもの

| 対象 | 長期履歴としての扱い |
|---|---|
| 正規化した各観測 | 有効な保存根拠に基づき継続保管。最新値だけに上書きせず、古さを削除理由にしない |
| 比較条件 | SKU・VRAM・PCIe/SXM・GPU台数・販売単位・地域・契約・専有/共有・税・通貨・単位と不明理由を当時の値で残す |
| 出典・時間・方法 | source URL/ID、観測時刻、source_dateと精度、取得scope/完全性、adapter/method/schema版、元config/hash、権利・例外判断の版を観測と結ぶ |
| 改定・訂正 | 当時見えていた値と後日の訂正を別の記録として残す。過去の原値を現在の値で置き換えない |
| 正常な再観測 | 価格不変でも観測済みを証明する。毎日値が変わることを正常条件にしない |
| 欠測・消失 | 取得失敗、partial、確認できた非掲載を区別する。Rebro掲載消失を売却成立にしない |
| 派生値 | 原通貨・原単位・decimal stringを残す。換算値にはFX observation ID、比較値には方法版と対象観測を結ぶ |
| 短期の投影証拠 | 現状の7日案は診断用コピーについての候補。削除しても上記の最小監査情報は履歴に残す。raw HTMLは保存しない |
| 制御記録 | 停止・取消し・削除・復元照合の記録を維持する。古いDB復元で削除対象や試行予算を復活させない |

本文hashだけでは元ページや抽出の正しさを再現できない。raw HTMLを保存しない制限下で、どこまで再検証できるかを明記する。将来の価値は保存年数だけでなく、比較可能性・連続性・出典と方法の追跡可能性で評価する。

## 契約で分ける四つの期間・判断

1. **初回の実行範囲:** 各社1試行・24時間窓という受入範囲は残す。これは初回をいつ実行できるかの条件であり、そのデータの寿命ではない。
2. **取得・分析の再確認:** 規約変更やreview期限では必要な取得/readを止める。Highreso旧版の境界も維持する。レビュー期限そのものから保存終了・削除義務を作らない。
3. **継続保存の根拠:** 提供者許諾による通常経路と、未確認事項を認識した所有者の個人研究例外を別々に記録する。後者も保存目的・対象・未解決事項・継続条件・停止/削除条件を明示して承認する。null、無回答、研究目標だけで保管を許可しない。
4. **削除の根拠:** 承認された明示的な保存期限、適用される削除義務、保存判断の取消し等を根拠付きで処理する。研究目標、容量節約、収集停止、分析レビューのリマインダーを削除根拠へ流用しない。

保存根拠が不明になった場合は、既存の根拠と適用義務を確認し、取得/readを停止して保存状態を独立に評価する。架空の無期限許可も、根拠のない30日猶予/強制削除も作らない。既に確定した削除期限を、新設定や復元で延長しない。

将来の契約更新・分析再開は元の観測や契約snapshotの書換えではなく、対象履歴を指定した追加の判断記録で表す。新しい許可が過去のデータにも適用するかを確認し、明示的な削除義務・取消しマーカーは上書きしない。

## v1との差分と今回のv2の到達点

| 現状 | 長期目的に向けた差分（実装範囲は下記） |
|---|---|
| `fixed_days`、1〜3650日の固定日数、絶対保存期限が必須 | source別の継続保存判断と明示的な終了条件。3650日を入れて10年問題が解決したと扱わない |
| 契約とrunが固定され、同じ契約の日時・条件更新を拒否 | 取得時snapshotを守った追加の保存/分析判断、対象履歴の再評価、期限・取消しの優先順位 |
| 各社初回1試行のみ | 受入後に別途承認する日次収集・観測連続性・同価格再観測・訂正履歴。初回予算を日付やID変更で迂回しない |
| local storeのコピー/バックアップ0のみ対応 | 許可条件を満たす自動バックアップ、コピー台帳、復元検証と期限/取消し反映。バックアップなしを10年運用の完成形にしない |
| CLIのmaintain/watch。再起動後の自動稼働は未接続 | 保守とバックアップの自動稼働・失敗検知・復元検証。日次の人手に依存しない |

通常research側には継続保存・履歴再評価の仕組みがあるが、提供者許諾未確認の個人研究例外へそのまま適用できない。権利をallowedに複製して流用せず、専用のauthority境界を維持して拡張する。v2のschema・前進0012・追加レビュー・暗号化snapshot・復元・自動保守を実装した。詳細と検証は[実装記録](../personal-continuing-20261018.md)。旧v1の期限は維持し、remote DBは変更していない。日次取得、同価格再観測・訂正等の個人例外の連続収集は次の独立した実装・承認範囲であり、今回完成したとは報告しない。

バックアップの保存先・頻度・保持・アクセス権、障害時に許容する欠損期間と復旧時間は別に具体化する。新DB、R2 archive、NAS転送、課金契約や本番リソースを、この目的の明確化だけで作成しない。容量の実測と予測は取得停止や増強の判断に使い、履歴の無断間引き・削除に使わない。

## 初回実収集へ進む前の受入条件

- 長期保存契約に合わせた例外経路を実装し、取得窓終了・定期review・分析停止後も、有効な保存根拠のある履歴が失われないことをsyntheticで確認する。
- 長期の時計進行、複数回の規約レビュー、契約更新、同価格再観測、訂正、欠測を経ても当初の観測・比較条件・方法版が照合できることを確認する。時計を進めたテストは10年間の実稼働実績ではない。
- コピー/復元を含む承認条件と自動維持方式を確定する。削除義務があるデータは期限に従い、古いコピーからも利用を再開しない。
- source別に承認済み実行契約を固定する。2案はv2のowner_continuingを提案するが、承認参照・日時・保存/コピー確認は未確定で、runtimeが拒否する状態を維持する。normalized_daysとstorage_untilのnullは単独の保存許可ではない。

初回を急ぐために短期削除契約で実データを取り、後から消えないように書き換える順序にはしない。実収集の前に、その最初の観測を将来の履歴へ残せる根拠と実装を揃える。
